# BUG-006: lexical_search ANDs every lexeme, so hybrid retrieval was dense-only

**Severity:** High (an entire retrieval branch returned nothing; RRF fused a single list)
**Status:** Fixed
**Scope:** `atlas_vector.repositories.PgVectorRepository.lexical_search`

## Summary

`lexical_search` built its query with `plainto_tsquery`:

```python
query = safunc.plainto_tsquery("english", text)
```

`plainto_tsquery` joins every lexeme with `&`, so a chunk matches only if it
contains **all** the terms. A natural-language question has six or more
lexemes, which makes the predicate effectively unsatisfiable over a small
corpus:

```
plainto_tsquery('english', 'What vector dimension is assigned to each chunk when a document is ingested?')
-> 'vector' & 'dimens' & 'assign' & 'chunk' & 'document' & 'ingest'
```

## Impact

Measured on the evaluation corpus (112 chunks, 40 judged queries):

- Before: lexical search returned **0 rows for all 40 queries**.
- `Retriever` therefore fused `[dense_hits, []]`, which is the dense ranking
  unchanged. `hybrid` scored identically to `full4096` on every metric
  (recall 92.5%, MRR 0.642, nDCG 71.2%, hit@1 45.0%) — the tell that the
  second list contributed nothing.
- Production behaved the same way: every request paid a second SQL round trip
  and a `ts_rank_cd` computation for a branch that could not match.

## Root cause

`plainto_tsquery` is AND semantics by design: it is meant for short search
boxes, not questions. Nothing in the pipeline rewrote the question into an OR
form, and nothing asserted that the lexical branch returned candidates, so the
failure was invisible — an empty list is a valid input to RRF.

## Fix

Build the `tsquery` from the question's lexemes, joined with `|`:

```python
lexemes = safunc.tsvector_to_array(safunc.to_tsvector("english", text))
terms = safunc.array_to_string(lexemes, " | ")
query = safunc.to_tsquery("english", safunc.coalesce(safunc.nullif(terms, ""), "atlasempty"))
```

`nullif`/`coalesce` guard the stopword-only case, where the lexeme array is
empty and `to_tsquery('english', '')` would raise. `ts_rank_cd` then ranks by
how many of the terms a chunk covers, which is the signal RRF needs.

## Verification

- `tests/test_repository_queries.py`: asserts the compiled predicate uses
  `to_tsquery` + `array_to_string` with `" | "` and never `plainto_tsquery`,
  and that the empty-input guard is present.
- Against the evaluation corpus: **0/40 queries return zero lexical rows**
  (median 50, capped by `k`); a stopword-only query returns `[]` without
  raising.
- `make eval-pipeline` re-run with a live lexical branch, recorded in
  `specs/verifications/EVAL-retrieval-hybrid.md`.

## Prevention

The evaluation harness now makes the branch observable: `hybrid` and
`full4096` diverging is expected, and identical scores across every metric are
a signal that one input list is empty rather than a finding. A future arm
should assert that each fusion input contributes at least one candidate.
