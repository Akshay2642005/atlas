# BUG-008: a failed ingest is permanent — the document row outlives the failure

**Severity:** High (one transient failure silently removes a document forever)
**Status:** Fixed
**Scope:** `atlas_vector.repositories.PgDocumentRepository.add`, `scripts/eval_retrieval._existing_checksums`

## Summary

`IngestPipeline.run` persists the document row *before* it validates or embeds
anything:

```python
document = Document(id=uuid.uuid4(), ..., status=DocumentStatus.PROCESSING,
                    checksum=checksum(spec.content))
await self._documents.add(document, spec.content)      # row + content committed
return await self._process(document, spec.content)     # guard, chunk, embed
```

`_process` marks the document `failed` on any exception. The row keeps its
`checksum`, and `documents` has `UNIQUE (tenant_id, checksum)`, so re-ingesting
the same bytes collides. The evaluation harness never even gets that far — it
skipped any checksum it already had:

```sql
SELECT checksum FROM documents WHERE tenant_id = :tenant
```

## Impact

Observed while ingesting the public documentation corpus:

- 21 documents were rejected by the injection guard (BUG-007) and marked
  `failed` with zero chunks.
- Re-running `make eval-ingest-docs` after fixing the guard reported
  **`ingested 0, skipped 929, failed 0`** — the 21 fixed documents were still
  unretrievable, and the run looked successful.
- `SELECT status, count(*) … GROUP BY 1` showed `failed | 21`; nothing else did.

The repository corpus had already lost a document the same way, unnoticed:
`specs/archive/research/enterprise-rag-features.md` sat in `atlas-eval` as
`failed` with zero chunks, rejected by the same guard, so every retrieval
measurement on that corpus was taken without it. After the fix, re-running
`make eval-ingest` recovered it (2 chunks). The fixture was then restored to
the 112-chunk snapshot the committed reports describe, so the two casualties
are recorded here rather than silently re-measured.

The same applies to a transient 504 from the embedder, a chunker error, or any
other one-off failure: the document is poisoned, not retried. On a 929-document
corpus, one bad night of upstream errors silently loses documents.

## Root cause

Two decisions combine badly:

1. The document row (and therefore the checksum) is committed before the work
   that can fail.
2. "Already ingested" was defined as "a row exists", not "a row produced chunks".

## Fix

**A retry replaces an attempt that produced no chunks.** `PgDocumentRepository.add`
deletes a document with the same `(tenant_id, checksum)` *only if it has no
chunks*, so a retry replaces the failed attempt instead of colliding with it.
Chunks and raw content cascade from the document row.

```python
await session.execute(
    delete(DocumentRow).where(
        DocumentRow.tenant_id == document.tenant_id,
        DocumentRow.checksum == document.checksum,
        ~exists(select(ChunkRow.id).where(ChunkRow.document_id == DocumentRow.id)),
    )
)
```

The condition is deliberately narrow. The upload route maps `IntegrityError` to
**409 "document already ingested"**, which is a product contract worth keeping:
a document that already produced chunks still collides, and an unconditional
replace would have silently turned that 409 into a re-ingest. "Produced no
chunks" is the same definition the harness now uses for "done", so the
repository and the harness agree on one invariant.

**The harness skips on output, not on row existence.** A checksum counts as
done only when the document produced chunks:

```sql
SELECT d.checksum FROM documents d
 WHERE d.tenant_id = :tenant
   AND EXISTS (SELECT 1 FROM chunks c WHERE c.document_id = d.id)
```

**A zero-chunk document is now loud.** `ingest` counts documents in the tenant
with no chunks and exits non-zero with a `WARNING … re-run to retry them`, so a
run that did not do what it claimed cannot report success.

The port docstring records the contract: re-adding the same
`(tenant_id, checksum)` replaces the earlier attempt.

## Verification

- `tests/test_document_repository.py` asserts that `add` issues the `DELETE`
  first, scopes it to tenant + checksum, restricts it to documents with no
  chunks, and then inserts the document and its content.
- Against the evaluation database, reproducing the exact failure: a `failed`
  document row with the corpus checksum and zero chunks was created by hand,
  then `ingest` was run on that file. Result: **one** document row, `indexed`,
  45 chunks — the stale attempt replaced, not skipped.
- The other half of the contract, also against the database: adding the same
  checksum again once the document has chunks raises `IntegrityError`, which
  the upload route maps to 409, and the existing 45 chunks are untouched.
- Re-running the same ingest skips it (`skipped 1`) as intended.
- With an unreachable zero-chunk document present the run exits **1** and prints
  the warning; with it removed the same run exits **0**.
- The real casualty above was recovered by `make eval-ingest` with no special
  handling: one `failed` document, re-ingested to 2 chunks.
- `make preflight` green (65 tests).

## Prevention

The invariant is "a document exists ⇒ either it has chunks or it is retryable".
Anything that reports ingest results should count zero-chunk documents, not
just rows: the original bug was invisible precisely because every count in the
summary line was consistent with success.
