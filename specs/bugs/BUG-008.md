# BUG-008: a failed ingest is permanent — the document row outlives the failure

**Severity:** High (one transient failure silently removes a document forever)
**Status:** Open
**Scope:** `atlas_ingest.pipeline.IngestPipeline.run`, `scripts/eval_retrieval._existing_checksums`

## Summary

`IngestPipeline.run` persists the document row *before* it validates or embeds
anything:

```python
document = Document(id=uuid.uuid4(), ..., status=DocumentStatus.PROCESSING,
                    checksum=checksum(spec.content))
await self._documents.add(document, spec.content)      # row + content committed
return await self._process(document, spec.content)     # guard, chunk, embed
```

`_process` marks the document `failed` on any exception. The row keeps its
`checksum`, and `documents` has
`UNIQUE (tenant_id, checksum)`, so the next ingest of the same bytes hits the
unique constraint — and the evaluation harness, which skips any checksum it
already has, never even gets that far:

```sql
SELECT checksum FROM documents WHERE tenant_id = :tenant
```

## Impact

Observed while ingesting the public documentation corpus:

- 21 documents were rejected by the injection guard (BUG-007) and marked
  `failed` with zero chunks.
- Re-running `make eval-ingest-docs` after fixing the guard reported
  **`ingested 0, skipped 929, failed 0`** — the 21 fixed documents were still
  unretrievable, and the run looked successful.
- `SELECT status, count(*) … GROUP BY 1` showed `failed | 21`, the only way to
  see the problem.

The same applies to a transient 504 from the embedder, a chunker error, or any
other one-off failure: the document is poisoned, not retried. On a 929-document
corpus, one bad night of upstream errors silently loses documents with no
signal beyond a log line that a later run will not reproduce.

## Root cause

Two separate decisions combine badly:

1. The document row (and therefore the checksum) is committed before the work
   that can fail.
2. "Already ingested" is defined as "a row exists", not "a row succeeded".

## Fix

Not yet applied. The intended shape:

- `PgDocumentRepository.add` replaces an existing `(tenant_id, checksum)` row
  instead of raising, so an ingest is retryable and idempotent; or
- `_existing_checksums` filters to documents that produced chunks, and the
  repository handles the conflict.

The first is the honest semantic: ingesting the same source again should
re-produce it, not collide. The harness skip is then a cost optimisation rather
than a correctness mechanism.

## Verification

Pending. The workaround used for the corpus run was to delete the 21 zero-chunk
rows by hand and re-ingest; that produced 775 chunks and a 929/929 corpus.

## Prevention

The harness should fail loudly when a tenant contains `failed` documents, rather
than reporting a clean `skipped 929` — the count of zero-chunk documents is the
signal that a run did not do what it claimed.
